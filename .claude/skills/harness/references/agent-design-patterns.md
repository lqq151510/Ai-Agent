# Agent 团队设计模式

## 执行模式: Agent 团队 vs Sub Agent

理解两种执行模式的核心差异，选择合适模式。

### Agent 团队 (Agent Teams) — 默认模式

团队 Leader 通过 `TeamCreate` 组队，成员以独立 Claude Code 实例运行。成员通过 `SendMessage` 直接通信，通过共享任务列表（`TaskCreate`/`TaskUpdate`）自协调。

```
[Leader] ←→ [成员A] ←→ [成员B]
  ↕          ↕          ↕
  └──── 共享任务列表 ────┘
```

**核心工具:**
- `TeamCreate`: 创建团队 + spawn 成员
- `SendMessage({to: name})`: 向特定成员发送消息
- `SendMessage({to: "all"})`: 广播（成本高，少用）
- `TaskCreate`/`TaskUpdate`: 共享任务列表管理

**特点:**
- 成员间可直接对话、挑战、验证
- 不经 Leader 的成员间信息交换
- 共享任务列表自协调（可自请求任务）
- 成员空闲时自动通知 Leader
- 可通过计划审批模式在执行危险操作前审查

**约束:**
- 每会话仅可 **激活** 一个团队（但可在 Phase 间解散重组）
- 不可嵌套团队（成员不能创建自己的团队）
- Leader 固定（不可移交）
- Token 成本较高

**团队重组模式:**
Phase 间需要不同专家组合时，按 保存上阶段产物到文件 → 清理团队 → 创建新团队 的顺序进行。上阶段产物保存在 `_workspace/` 中，新团队可通过 Read 访问。

### Sub Agent (Sub-agents) — 轻量模式

主 Agent 通过 `Agent` 工具创建 Sub Agent。Sub Agent 仅将任务结果返回主 Agent，彼此不通信。

```
[主] → [SubA] → 结果返回
    → [SubB] → 结果返回
    → [SubC] → 结果返回
```

**核心工具:**
- `Agent(prompt, subagent_type, run_in_background)`: 创建 Sub Agent

**特点:**
- 轻量快速
- 结果摘要返回主上下文
- Token 高效

**约束:**
- Sub Agent 间不可通信
- 主 Agent 承担所有协调
- 无法实时协作/挑战

### 模式选择决策树

```
Agent 数量 ≥ 2 ?
├── Yes → Agent 间需要通信?
│         ├── Yes → Agent 团队（默认值）
│         │         交叉验证、发现共享、实时反馈提升质量。
│         │
│         └── No → Sub Agent 也可
│                  仅需结果传递的 生成-验证、专家池 等场景。
│
└── No (1 个) → Sub Agent
              单 Agent 组队无必要。
```

> **核心原则:** Agent 团队是默认选项。选择 Sub Agent 时需自问"成员间通信真的不必要吗？"

## Agent 团队架构类型

### 1. Pipeline（管道）
顺序任务流。上一 Agent 的输出为下一 Agent 的输入。

```
[分析] → [设计] → [实现] → [验证]
```

**适合:** 各阶段强依赖上阶段产物
**示例:** 小说写作 — 世界观 → 角色 → 情节 → 写作 → 编辑
**注意:** 瓶颈会延迟整个管道。尽量将各阶段设计为独立。
**团队模式适配性:** 顺序依赖强，团队模式优势有限。但管道内如有并行段则团队模式有用。

### 2. Fan-out/Fan-in（扇出/扇入）
并行处理后结果整合。独立任务同时执行。

```
         ┌→ [专家A] ─┐
[分发] → ├→ [专家B] ─┼→ [整合]
         └→ [专家C] ─┘
```

**适合:** 同一输入需要不同视角/领域的分析
**示例:** 综合调研 — 官方/媒体/社区/背景同步调查 → 整合报告
**注意:** 整合阶段的质量决定整体质量。
**团队模式适配性:** Agent 团队最自然的模式。**必须使用 Agent 团队。** 成员间共享发现、相互挑战，一个 Agent 的发现可实时修正另一个 Agent 的调查方向，质量远超单独调查。

### 3. Expert Pool（专家池）
按场景选择合适专家调用。

```
[路由] → { 专家A | 专家B | 专家C }
```

**适合:** 不同输入类型需要不同处理
**示例:** 代码审查 — 安全/性能/架构专家中仅调用相关领域
**注意:** 路由的分类准确度是关键。
**团队模式适配性:** Sub Agent 更合适。仅调用需要的专家，常驻团队不必要。

### 4. Producer-Reviewer（生成-验证）
生成 Agent 和验证 Agent 成对运作。

```
[生成] → [验证] → (有问题) → [生成] 重新执行
```

**适合:** 产出质量保证重要且存在客观验证标准
**示例:** 漫画 — artist 生成 → reviewer 审查 → 问题面板重新生成
**注意:** 必须设置最大重试次数（2~3 次）防止无限循环。
**团队模式适配性:** Agent 团队有用。SendMessage 实现生成者↔验证者实时反馈交换。

### 5. Supervisor（监督者）
中央 Agent 管理工作状态，动态向子 Agent 分配任务。

```
         ┌→ [WorkerA]
[监督者] ─┼→ [WorkerB]    ← 监督者观察状态动态分配
         └→ [WorkerC]
```

**适合:** 工作量可变或需运行时决定任务分配
**示例:** 大规模代码迁移 — 监督者分析文件列表，向 Workers 分配批次
**与 Fan-out 的区别:** Fan-out 预先固定分配任务，监督者观察进度动态调整
**注意:** 委派单位足够大以免监督者成为瓶颈。
**团队模式适配性:** Agent 团队的共享任务列表与监督者模式自然匹配。TaskCreate 注册任务，成员自请求。

### 6. Hierarchical Delegation（层级委托）
上级 Agent 向下级递归委托。复杂问题逐级分解。

```
[总负责] → [组长A] → [执行者A1]
                  → [执行者A2]
       → [组长B] → [执行者B1]
```

**适合:** 问题自然呈层级分解结构
**示例:** 全栈应用开发 — 总负责 → 前端组长 → (UI/逻辑/测试) + 后端组长 → (API/DB/测试)
**注意:** 深度 3 级以上延迟和上下文损失大。建议 2 级以内。
**团队模式适配性:** Agent 团队不可嵌套（成员不能创建团队）。1 级用团队，2 级用 Sub Agent，或扁平化为单一团队。

## 复合模式

实战中复合模式比单一模式更常见:

| 复合模式 | 构成 | 示例 |
|----------|------|------|
| **Fan-out + 生成-验证** | 并行生成后各自验证 | 多语言翻译 — 4 种语言并行翻译 → 各母语审查员验证 |
| **Pipeline + Fan-out** | 顺序阶段中部分并行化 | 分析(顺序) → 实现(并行) → 集成测试(顺序) |
| **Supervisor + Expert Pool** | 监督者动态调用专家 | 客户咨询处理 — 监督者分类咨询后分配合适专家 |

### 复合模式中的执行模式

**默认所有复合模式使用 Agent 团队。** 成员间活跃沟通是结果质量的核心动力。

| 场景 | 推荐模式 | 理由 |
|---------|----------|------|
| **调研 + 分析** | Agent 团队 | 调查员间发现共享，冲突信息实时讨论 |
| **设计 + 实现 + 验证** | Agent 团队 | 设计者↔实现者↔验证者间反馈回路 |
| **监督者 + Worker** | Agent 团队 | 共享任务列表动态分配，Worker 间进度共享 |
| **生成 + 验证** | Agent 团队 | 生成者↔验证者实时反馈减少返工 |

> 仅当单个 Agent 执行完全隔离的一次性任务时，才考虑混合 Sub Agent。

## Agent 类型选择

调用 Agent 时通过 Agent 工具的 `subagent_type` 参数指定类型。Agent 团队的成员也可使用自定义 Agent 定义。

### 内置类型

| 类型 | 工具访问 | 适用场景 |
|------|----------|-----------|
| `general-purpose` | 全部（含 WebSearch、WebFetch） | Web 调查、通用任务 |
| `Explore` | 只读（无 Edit/Write） | 代码库探索、分析 |
| `Plan` | 只读（无 Edit/Write） | 架构设计、计划制定 |

### 自定义类型

在 `.claude/agents/{name}.md` 中定义 Agent，通过 `subagent_type: "{name}"` 调用。自定义 Agent 可访问全部工具。

### 选择标准

| 情境 | 推荐 | 理由 |
|------|------|------|
| 角色复杂且多会话复用 | **自定义类型**（`.claude/agents/`） | 角色和工作原则以文件管理 |
| 简单调查/收集且 Prompt 足够 | **`general-purpose`** + 详细 Prompt | 无需 Agent 文件，Prompt 包含指示 |
| 仅需读代码（分析/审查） | **`Explore`** | 防止误修改文件 |
| 仅需设计/计划 | **`Plan`** | 专注分析，防止代码变更 |
| 需要修改文件的实现任务 | **自定义类型** | 全部工具访问 + 专业指示 |

**原则:** 所有 Agent 必须定义为 `.claude/agents/{name}.md` 文件。内置类型也需创建 Agent 定义文件，明示角色、原则、协议。只有存为文件才能下个会话复用，只有明示团队通信协议才能保证协作质量。

**模型:** 所有 Agent 使用 `model: "opus"`。Agent 工具调用时必须指定 `model: "opus"` 参数。

## Agent 定义结构

```markdown
---
name: agent-name
description: "1-2 句话角色描述。列出触发关键词。"
---

# Agent Name — 角色一句话总结

你是 [领域] 的 [角色] 专家。

## 核心角色
1. 角色1
2. 角色2

## 工作原则
- 原则1
- 原则2

## 输入/输出协议
- 输入: [从何处接收什么]
- 输出: [向何处写入什么]
- 格式: [文件格式、结构]

## 团队通信协议（Agent 团队模式）
- 消息接收: [从谁接收什么消息]
- 消息发送: [向谁发送什么消息]
- 任务请求: [从共享任务列表请求什么类型的任务]

## 错误处理
- [失败时行为]
- [超时行为]

## 协作
- 与其他 Agent 的关系
```

## Agent 拆分标准

| 标准 | 拆分 | 合并 |
|------|------|------|
| 专业性 | 领域不同则拆分 | 领域重叠则合并 |
| 并行性 | 可独立执行则拆分 | 顺序依赖则考虑合并 |
| 上下文 | 上下文负担大则拆分 | 轻量快速则合并 |
| 复用性 | 其他团队也用则拆分 | 仅本团队用则考虑合并 |

## Skill vs Agent 区分

| 区分 | Skill | Agent |
|------|-------------|-----------------|
| 定义 | 过程性知识 + 工具包 | 专家角色 + 行为原则 |
| 位置 | `.claude/skills/` | `.claude/agents/` |
| 触发 | 用户请求关键词匹配 | Agent 工具显式调用 |
| 大小 | 小~大（工作流） | 小（角色定义） |
| 用途 | "如何做" | "谁来做" |

Skill 是 Agent 执行任务时参考的 **过程性指南**。
Agent 是利用 Skill 的 **专家角色定义**。

## Skill ↔ Agent 连接方式

Agent 利用 Skill 的 3 种方式:

| 方式 | 实现 | 适合场景 |
|------|------|-----------|
| **Skill 工具调用** | Agent Prompt 中明确 `用 Skill 工具调用 /skill-name` | Skill 是独立工作流且用户可调用 |
| **Prompt 内联** | Agent 定义内直接包含 Skill 内容 | Skill 简短（50 行以下）且仅本 Agent 专用 |
| **Reference 加载** | 需要时 `Read` 加载 Skill 的 references/ 文件 | Skill 内容大且仅条件性需要 |

推荐: 复用性高用 Skill 工具，专用则内联，大容量则 Reference 加载。
