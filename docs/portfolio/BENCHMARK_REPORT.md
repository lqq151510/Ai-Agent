## 2. RAG 检索策略对比基准 (Retrieval Benchmark - 算法测试集评测)

在包含分布式事务、Kafka 协调者、Milvus 索引调优、JWT 鉴权、多级缓存一致性等典型技术文档语料库（涵盖精确代码符号、技术参数名与自然语言概念，共 8 篇文档、13 组测试查询）上，通过 `RAGEvaluationBenchmarkTest` 测试套件量化验证了三种检索策略的排序融合表现（注：该基准用于验证 RRF 倒数排名融合算法在多源结果冲突时的排序稳定性与防漏检特性，基于各路检索返回的相对排名进行融合计算，无需投影至统一向量空间）：

| 检索策略 (Retrieval Strategy) | Hit@1 准确率 | Hit@3 召回率 | MRR 评分 (Mean Reciprocal Rank) | 平均检索耗时 (ms) | 核心特性与工程权衡说明 |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **纯关键词检索 (Keyword / FTS)** | 76.9% | 84.6% | 0.8327 | ~1 ms | 对专有名词、API、类名精确命中极佳；对模糊语义理解较弱 |
| **纯密集向量打分 (Dense Vector)** | 84.6% | 92.3% | 0.8942 | ~4 ms | 语义泛化能力强；但在生僻缩写或特定参数名上容易发生语义漂移 |
| **RRF 混合融合检索 (Reciprocal Rank Fusion)** | **84.6%** | **92.3%** | **0.8718** | ~9 ms | **多路召回鲁棒性均衡**：通过 \(Score = \sum \frac{1}{k + rank_i}\) (\(k=60\)) 平衡稀疏与密集排名，兼顾专有名词精确匹配与语义召回 |

### 关键结论与工程权衡（面试关键点）：
1. **RRF 在 Hit@3 保持与向量打分持平的高位（92.3%）**，显著优于纯关键词的 84.6%，同时有效改善了纯向量检索面对生僻配置参数（如 `efConstruction`、`ackMode`）时的语义遗漏问题。
2. **客观理解 RRF 的 MRR 表现**：RRF 的 MRR (0.8718) 高于纯关键词 (0.8327)，但略低于纯向量 (0.8942)。原因在于 RRF 引入的平滑衰减常数 \(k=60\) 会在不同召回源对首位文档排序产生分歧时适度平滑得分，牺牲了极个别单一源置信度极高的微小 MRR，换取了跨召回源的整体排序稳定性与防漏检能力。
3. **多租户元数据预过滤（Pre-filtering）**：在执行向量搜索前将 `userId` 条件直接下推到底层向量请求，实现租户级数据逻辑隔离与跨租户防穿透，杜绝内存后过滤导致的候选集污染。

## 3. 大模型语义缓存 (Semantic Cache) 离线敏感度推演（设计阶段原型探索）

> **【注意】**：以下数据基于蒙特卡洛随机抽样模型（`scripts/benchmark/rag_cache_benchmark.py`），用于在开发初期推演语义缓存对长尾延迟的理论改善边界，**非线上真实环境物理压测，不得作为生产实测数据写入简历**。

基于 LangChain4j 向量余弦相似度（设定判定阈值 \(\ge 0.92\)）对高频与相似问答进行语义拦截：

| 评估维度 (Dimension) | 无语义缓存基线 (Full LLM 模拟) | 启用语义缓存 (65% 目标命中率推演) | 理论推演收益说明 |
| :--- | :---: | :---: | :---: |
| **端到端平均延迟 (Avg Latency)** | ~1350 ms | ~500 ms | 命中请求无需大模型推理排队 |
| **单次命中响应 (命中场景)** | ~1350 ms | **< 30 ms** | 仅耗费本地向量计算与比对延迟 |
| **Token 消耗** | 全量计费 | 命中部分 0 Token | 避免高频重复相似问答带来的 API 消耗 |

### 工程经验沉淀（面试关键点）：
- **阈值选型原则**：阈值过高（如 0.98）导致缓存命中率极低（< 10%）；阈值过低（如 0.85）会导致“近义但逻辑相反”的问题发生误命中（例如“如何开启事务”误命中“如何关闭事务”）。工程实践表明 **0.92 ~ 0.94** 为合理平衡点。
- **瞬态与持久化边界**：语义缓存定位为高频瞬态加速层，重启可重建；主知识向量索引定位为持久资产，支持落盘快照与损坏自愈。

## 4. 多级缓存架构理论设计模型与一致性保障（Caffeine L1 + Redis L2）

针对知识条目与元数据读取，设计 **Caffeine 本地内存 L1 + Redis 分布式 L2 + 关系型数据库** 的多级防击穿缓存拓扑：

```
[用户请求] 
    │
    ├───> [L1: Caffeine 本地内存]  ──> 纳秒/微秒级响应 (进程内无网络开销)
    │
    ├───> [L2: Redis 分布式缓存]   ──> 毫秒级网络 I/O 响应 (跨节点共享热点)
    │
    └───> [DB: PostgreSQL/H2]     ──> 磁盘 I/O (回填 L2 与 L1)
```

### 延迟理论加权估算模型（供方案设计与容量推演）：
- 假设在成熟业务读场景下，L1 承载 80% 读流量（平均耗时 ~0.15ms），L2 承载 15% 读流量（平均耗时 ~2.1ms），DB 承载 5% 穿透流量（平均耗时 ~18.5ms）：
- 理论加权平均耗时估算为：\(0.80 \times 0.15\text{ms} + 0.15 \times 2.10\text{ms} + 0.05 \times 18.50\text{ms} = 1.36\text{ms}\)。
- 此模型展示了通过进程内缓存阻断网络 RTT 对平均延迟的显著收益，但严禁将此理论加权值（1.36ms）或静态推演吞吐冒充为生产真实压测指标。

### 防御机制与一致性保障（核心面试亮点）：
1. **防缓存穿透**：查询空对象时缓存短过期时间的特殊空标记（Null Object），结合参数校验拦截非法 ID。
2. **防缓存击穿**：对热点条目采用互斥分布式锁（Redis / 本地并发锁），仅允许一个线程回源 DB，其余线程等待复用缓存。
3. **防缓存雪崩**：基础 TTL 设置随机抖动（如 300s + \(\text{rand}(0, 60)\)s），避免整批缓存同一秒失效导致 DB 压力骤增。
4. **双写一致性**：更新数据时先更新 DB，再删除 Redis 缓存（Cache-Aside 模式）；结合本地短 TTL 兜底，保证并发读写下的最终一致性。
