## 1. 这份基线能说明什么 / 不能说明什么

**能说明**：Knowledge Desk 五步链路在**桌面版运行形态**（`desktop` profile + 内嵌 H2 + Flyway `classpath:db/h2`）下的**后端处理开销**，可作为后续性能回归的比较基准。

**不能说明**：

- **不含真实大模型时延**。模型是进程内 OpenAI 兼容 mock，`assistant_chat` 度量的是"HTTP 入参 → 上下文组装 → 模型往返(mock) → 落库"的链路开销；
- **不是 Postgres/生产形态**。H2 内存库、单实例、无 Redis（Caffeine 内存缓存）、无 Kafka；
- **不是并发压测**。串行采样，反映的是单请求延迟分布，不是吞吐上限。

### 3.1 方法与两个容易误读的点

- **百分位算法**：升序后取 `ceil(p*n)-1`（最近秩法），样本量 30 时 p99 即最大值，因此 `p99 == max` 是算法结果，不代表长尾已收敛。若要更稳的 p99，用 `-De2e.perf.iterations=200` 复跑。
- **语义缓存**：`SemanticCacheService` 命中阈值 0.95。基线用例对每次对话使用**全新随机词元**，确保走冷路径；否则会测成"缓存命中"（更早一次未加随机词元的试跑，`assistant_chat` p50 只有 4.25ms，就是缓存命中路径，已不作为基线）。

## 5. 与真实产品的差距（解读时请带上下文）

| 维度 | 本基线 | 生产/桌面真实使用 |
| --- | --- | --- |
| 模型 | 进程内 mock，零网络 | 真实 LLM（或本地推理），秒级~十秒级 |
| 整理策略 | 无模型源 → 启发式整理 | 配置了摘要模型源时会走模型整理（`KnowledgeOrganizerService`） |
| 数据库 | H2 内存 | Postgres / 桌面 H2 文件库（含磁盘 IO） |
| 向量检索 | 内存 store + 确定性 mock 向量 | 真实 embedding（Milvus/PgVector/本地回退） |
| 并发 | 串行 | 多用户并发、连接池竞争 |

因此这组数字应当作为**后端链路开销的下界基线**，而不是端到端用户体验指标。
